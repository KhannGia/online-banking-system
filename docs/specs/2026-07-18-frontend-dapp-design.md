# SavingCore dApp — Frontend Design

**Date:** 2026-07-18
**Scope:** React frontend sub-project (assignment §7.3). Depends on the deployed contracts (`MockUSDC`, `VaultManager`, `SavingCore`) already built and merged to `main`.
**Student ID:** K234141651 (variant values: grace 3 days, APR 225 bps, penalty 550 bps, tenor 180 days).

## 0. Goal & Scope

A React dApp that connects MetaMask and lets a user:

- **View available plans** and **open a deposit** (approve → openDeposit).
- **View their active deposits** with live status, principal, locked APR, and maturity/grace countdowns.
- **Withdraw or renew** a deposit (withdraw at maturity, early withdraw, manual renew).

Beyond the assignment minimum (the user wants a complete submission), the UI also surfaces:

- **Bonus C1** — a "Claim interest" action when a deposit has `pendingInterest > 0`.
- **Bonus G** — an "Auto-renew" action (permissionless keeper) once a deposit passes its grace period.
- **Admin page** (visible only to the contract owner) — plan management, vault funding, the **bonus F** timelocked withdrawal (schedule/execute/cancel), fee receiver, pause/unpause, keeper-reward rate, plus a MockUSDC mint helper for demos.

**Not** in scope: a backend, indexer/subgraph, contract changes, or public mainnet deployment. Enumeration is done client-side against the chain (see §5.2).

## 3. Contract Wiring (@wagmi/cli)

`wagmi.config.ts` generates `src/generated.ts` from the Hardhat project. Per-chain
addresses are built programmatically by reading each deployment JSON that exists
(localhost always; sepolia only after a Sepolia deploy), so there are no hand-typed
addresses:

```ts
import { defineConfig } from '@wagmi/cli'
import { hardhat, react } from '@wagmi/cli/plugins'
import { existsSync, readFileSync } from 'node:fs'

const NAMES = ['MockUSDC', 'VaultManager', 'SavingCore'] as const
const NETS = { 31337: 'localhost', 11155111: 'sepolia' } as const

// contract -> { chainId: address } for whichever deployment files exist
function addressesFor(name: string) {
  const map: Record<number, `0x${string}`> = {}
  for (const [chainId, net] of Object.entries(NETS)) {
    const path = `../hardhat-temp/deployments/${net}/${name}.json`
    if (existsSync(path)) map[Number(chainId)] = JSON.parse(readFileSync(path, 'utf8')).address
  }
  return map
}

export default defineConfig({
  out: 'src/generated.ts',
  plugins: [
    hardhat({
      project: '../hardhat-temp',
      include: NAMES.map((n) => `${n}.json`),
      deployments: Object.fromEntries(NAMES.map((n) => [n, addressesFor(n)])),
    }),
    react(),
  ],
})
```

This yields typed ABIs (`savingCoreAbi`), per-chain addresses (`savingCoreAddress`), and hooks (`useReadSavingCore*`, `useSimulateSavingCore*`, `useWriteSavingCore*`, `useWatchSavingCore*Event`).

`src/generated.ts` is **committed** (not gitignored): local Hardhat deploy addresses are deterministic (fixed deployer + nonce order → identical addresses on every fresh node), so committing lets a grader build and run the frontend out of the box without first running codegen. Regenerate it with `npm run codegen` (`wagmi generate`) whenever addresses change (e.g. after a Sepolia deploy).

The Sepolia addresses come from `deployments/sepolia/*.json` once the contracts are deployed there (§10.2) — `addressesFor` picks them up automatically, so no manual editing.

`npm run codegen` runs **two** steps: `wagmi generate` (ABIs + addresses) and `node scripts/sync-deploy-blocks.mjs`, which writes `src/config/deployBlocks.json` as `{ "31337": <block>, "11155111": <block> }` from each network's `SavingCore.json` `receipt.blockNumber`. That file is committed and consumed by `deployFromBlock()` — see §5.2 for why the real block matters.

## 4. Chains & Wallet Config

`src/config/wagmi.ts` uses RainbowKit's `getDefaultConfig`:

```ts
export const config = getDefaultConfig({
  appName: 'SavingCore Bank',
  projectId: import.meta.env.VITE_WC_PROJECT_ID ?? 'demo',
  chains: [hardhat, sepolia],       // viem/wagmi built-in chain objects
  transports: {
    [hardhat.id]: http('http://127.0.0.1:8545'),
    [sepolia.id]: http(import.meta.env.VITE_SEPOLIA_RPC ?? undefined),
  },
})
```

`main.tsx` wraps the app in `WagmiProvider` → `QueryClientProvider` → `RainbowKitProvider`.

**ChainGuard** covers two distinct failure modes, because with two supported chains a user can easily land on one where nothing is deployed:

1. **Unsupported chain** — connected chain is neither 31337 nor 11155111 → "switch network" banner, writes disabled.
2. **Supported chain, no deployment** — `getAddress()` returns `undefined` for that chainId (e.g. the user switches to Sepolia before the contracts were deployed there) → a distinct "Contracts are not deployed on this network yet" banner, writes disabled. Without this the app would silently render empty plan/deposit lists and look broken.

MetaMask injected works without a WalletConnect projectId; the projectId only enriches the RainbowKit modal.

## 5. Data Layer

### 5.1 Reads

- `usePlans()` — reads `planCount()`, then multicalls `plans(0..n-1)`. Returns `Plan[]` with `{ planId, tenorDays, aprBps, minDeposit, maxDeposit, earlyWithdrawPenaltyBps, enabled }`.
- `useSystemState()` — reads `SavingCore.owner()`, `SavingCore.paused()`, `SavingCore.keeperRewardBps()`, `SavingCore.GRACE_PERIOD()`, `VaultManager.feeReceiver()`, `VaultManager.vaultBalance()`, `VaultManager.paused()`.
- `useIsOwner()` — `SavingCore.owner()` === connected address (case-insensitive).

### 5.2 Deposit enumeration (`useDeposits(address)`)

`SavingCore` is a plain ERC-721 (no `ERC721Enumerable`) and `DepositOpened`'s `owner` arg is **not indexed**, so there is no on-chain "deposits of X" query. The hook therefore:

1. `getLogs` for `DepositOpened` from the contract's deployment block (`deployFromBlock(chainId)`, backed by the generated `deployBlocks.json`) to `latest`.
2. Collect candidate `depositId`s, filtering to logs where `owner == connectedAddress` (client-side; also include ids where a later `Renewed` minted to the user).
3. Multicall `deposits(id)` and `ownerOf(id)` for each candidate; keep those where `ownerOf(id) == connectedAddress` (covers NFTs bought/transferred in).
4. Return the enriched `DepositView[]` (see §5.4).

**The `fromBlock` must be the real deployment block on Sepolia**, not `0`. Sepolia has millions of blocks, and public RPCs typically reject or time out on unbounded `getLogs` ranges (many cap a query at ~10k blocks). Scanning from the deployment block keeps the query to the handful of blocks that can actually contain our events. On the local Hardhat chain the chain is short, so its recorded block (usually a small number) is equally fine. This is why `deployBlocks.json` is generated rather than hardcoded.

If a Sepolia scan ever exceeds an RPC's range cap, `useDeposits` should page the scan in fixed block windows (e.g. 10k) from the deployment block to `latest` rather than raising `fromBlock`.

For a local demo this is instant; on Sepolia the bounded `fromBlock` keeps it cheap. Documented as a known trade-off of not using `ERC721Enumerable`.

### 5.3 Formatting (`lib/format.ts`)

- `formatUsdc(bigint) → string` and `parseUsdc(string) → bigint` at **6 decimals** (`viem` `formatUnits`/`parseUnits` with `6`).
- `bpsToPercent(bps) → string` (e.g. `225 → "2.25%"`).
- `formatCountdown(seconds) → string` (e.g. `"2d 4h 11m"`).

### 5.4 Deposit view logic (`lib/deposit.ts`, pure, unit-tested)

`deriveDepositView(deposit, now, gracePeriodSecs, systemPaused)` returns:

```ts
{
  statusLabel: 'Active' | 'Withdrawn' | 'Manually renewed' | 'Auto-renewed',
  isActive: boolean,
  isMatured: boolean,                 // now >= maturityAt
  isPastGrace: boolean,               // now >= maturityAt + grace
  secondsToMaturity: number,
  secondsToGraceEnd: number,
  hasPendingInterest: boolean,        // pendingInterest > 0
  actions: {
    withdrawAtMaturity: boolean,      // isActive && isMatured && !systemPaused
    earlyWithdraw: boolean,           // isActive && !isMatured && !systemPaused
    renew: boolean,                   // isActive && isMatured && !systemPaused
    autoRenew: boolean,               // isActive && isPastGrace && !systemPaused
    claimInterest: boolean,           // hasPendingInterest && !systemPaused
  }
}
```

These booleans exactly mirror the contract's require-guards (`>=` maturity, `>=` maturity+grace, `< maturity` for early, status Active), so the UI never offers an action that would revert. This function is the primary unit-test target.

## 6. Screens & Components

### 6.1 Header
RainbowKit `ConnectButton`, a network badge, and `ChainGuard`. Tab nav: **Deposit** · **My Deposits** · **Admin** (Admin tab hidden unless `useIsOwner()`).

### 6.2 PlansView + OpenDepositDialog
Grid of plan cards: tenor (days), APR (`bpsToPercent`), penalty, min/max, enabled badge. Each enabled plan has "Open deposit" → dialog with an amount input (validated against min/max and the user's MockUSDC balance), a live interest preview (calls `previewInterest` after open, or computes it client-side for the quote using the same formula), and a two-step flow (§7.1): approve `SavingCore` for `amount`, then `openDeposit(planId, amount)`. Disabled plans show but can't be opened.

### 6.3 MyDeposits + DepositRow + RenewDialog
Table of the user's deposits (`useDeposits`). Each row shows id, plan, principal (`formatUsdc`), locked APR, status, a maturity or grace countdown, and `pendingInterest` if any. Row actions are driven by `deriveDepositView().actions`:
- **Withdraw** → `withdrawAtMaturity(id)`.
- **Early withdraw** → `earlyWithdraw(id)`, behind a confirm showing the 550-bps penalty and that interest is forfeited.
- **Renew** → RenewDialog picks an enabled `newPlanId` → `renewDeposit(id, newPlanId)`.
- **Claim interest** → `claimInterest(id)` (shown when `pendingInterest > 0`).
- **Auto-renew** → `autoRenewDeposit(id)` (shown when past grace); labeled as the permissionless keeper action, notes the keeper reward.

### 6.4 AdminPanel (owner only)
- **Plans:** `createPlan(tenorDays, aprBps, minDeposit, maxDeposit, penaltyBps)` with a form pre-filled to the personal-variant defaults (180/225/0/0/550); `updatePlan(planId, newAprBps)`; `enablePlan`/`disablePlan`.
- **Vault:** `fundVault(amount)` (approve `VaultManager` → fund); current `vaultBalance()`; **timelock (F)**: `scheduleWithdrawVault(amount)`, then a live countdown to `withdrawExecutableAt`, `executeWithdrawVault()`, `cancelScheduledWithdrawal()`.
- **Config:** `setFeeReceiver(addr)`, `setKeeperRewardBps(bps)`, `pause()`/`unpause()` on both SavingCore and VaultManager (with clear labels for which contract).
- **Demo helper:** `MockUSDC.mint(to, amount)` to fund test accounts.

### 6.5 TxButton
A shared component wrapping `useWriteContract` → `useWaitForTransactionReceipt`, driving: disabled while pending, a toast per phase (pending/confirmed/reverted), and query invalidation on success so plans/deposits/balances refetch.

**Deviation from the original design:** this component was planned to also wrap `useSimulateContract`, running a dry-run before `useWriteContract` so a reverting call fails fast (no wallet popup at all). The shipped implementation skips simulation and calls `writeContract` directly. The consequence is that a reverting transaction only surfaces its failure after the user has already signed and submitted it, rather than being caught before the wallet prompt appears. This is mitigated by three layers that keep the UI from offering a reverting action in the first place: `deriveDepositView`'s contract-mirroring gating (row actions are hidden unless the contract's require-guards would pass), per-form input validation (amount bounds, address checks) before a button is even enabled, and `decodeRevert`-based toasts that give a friendly message on the rare revert that does slip through (e.g. a race with another actor's transaction).

## 7. Transaction Flows & Error Handling

### 7.1 Two-step token approvals
`openDeposit` (pulls user USDC) and `fundVault` (pulls owner USDC) each need an ERC-20 `approve` first. The dialog reads current `allowance`; if `< amount`, it shows an "Approve" step, then enables the main action. Uses exact-amount approvals.

### 7.2 Revert decoding (`lib/errors.ts`)
Contracts revert with plain strings (`"not matured"`, `"plan disabled"`, `"already matured"`, `"grace not passed"`, `"nothing pending"`, `"bad apr"`, …) and OZ custom errors (`OwnableUnauthorizedAccount`, `EnforcedPause`, `ReentrancyGuardReentrantCall`). `errors.ts` maps these to friendly toast messages; unknown reverts show the raw reason.

### 7.3 Refresh
After a confirmed tx, invalidate the relevant react-query keys (plans, the user's deposits, balances, system state). Optionally subscribe to `DepositOpened`/`Withdrawn`/`Renewed` via `useWatch*Event` to reflect other actors (e.g. a keeper auto-renewing) live.

### 7.4 Guard states
- Not connected → CTA to connect (RainbowKit modal).
- Wrong/unsupported chain → ChainGuard banner + switch prompt; writes disabled.
- System paused → open/withdraw/renew actions disabled with a "system paused" note (mirrors the contract).

## 8. Testing

Proportionate to a demo frontend (the assignment's >90% coverage requirement is for contracts, not the UI):

- **Vitest unit tests** for the pure logic that would otherwise be easy to get subtly wrong:
  - `lib/deposit.ts` `deriveDepositView` — matured/early/grace boundaries (`>=` vs `<`), action availability per status, pending-interest gating, paused gating. Mirrors the contract's own boundary tests.
  - `lib/format.ts` — `formatUsdc`/`parseUsdc` round-trips at 6 decimals, `bpsToPercent`, `formatCountdown`.
- **Manual/scripted verification** of the wallet flows against a local Hardhat node during the demo (no automated E2E — out of proportion for this deliverable).

## 10. Run & Deploy

### 10.1 Local (Hardhat)

1. In `hardhat-temp/`: `npx hardhat node` (terminal 1).
2. In `hardhat-temp/`: `npx hardhat deploy --network localhost` (terminal 2) — writes `deployments/localhost/*.json`.
3. In `frontend/`: `npm run codegen` (regenerates `src/generated.ts` + `deployBlocks.json`), then `npm run dev`.
4. MetaMask: add/select the `localhost:8545` network (chainId 31337), import a Hardhat test account, use the Admin "mint" helper to get MockUSDC.

### 10.2 Sepolia (a supported target, not an afterthought)

Sepolia is one of the two chains the app ships with, so it gets a real deployment — the same `deploy/1-deploy.ts` runs against it and creates the same personal-variant default plan (180 days / 225 bps / 550 bps).

**User-supplied prerequisites** (cannot be automated here): a deployer private key with Sepolia ETH from a faucet, set as `TESTNET_PRIVATE_KEY` in `hardhat-temp/.env`, and optionally `ETHERSCAN_API` for verification.

1. In `hardhat-temp/`: `npx hardhat deploy --network sepolia` — writes `deployments/sepolia/*.json` (address, ABI, and `receipt.blockNumber`).
2. Optionally verify: `npx hardhat verify --network sepolia <address> <constructorArgs…>` for each contract (hardhat-verify and the `sepolia` etherscan key are already configured).
3. Fund the vault so interest is payable on Sepolia: use the Admin panel (mint MockUSDC → approve → `fundVault`), since a fresh deployment starts with an empty interest pool.
4. In `frontend/`: `npm run codegen` — picks up the Sepolia addresses **and** the real deployment block automatically; commit the regenerated `generated.ts` and `deployBlocks.json`.
5. In the app: switch the wallet to Sepolia; the same UI works against the deployed contracts.

Because `deployFromBlock` now returns the true Sepolia deployment block, the `DepositOpened` scan stays inside public-RPC range limits (§5.2).
